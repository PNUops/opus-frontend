# OPUS Browser QA 운영 가이드

- **문서 성격:** OPUS 프론트엔드 팀의 Browser QA 운영 표준 및 개발자 사용 가이드
- **적용 범위:** 이 가이드는 로컬에 구현된 도메인별 Playwright Test Runner 구조를 기준으로 합니다. 구체적인 실행 방법·설정·로컬 검증 기록은 [구현·검증 참고 문서](./browser-qa-implementation.md)에서 확인하세요.
- **대상:** OPUS 프론트엔드 개발자, PR 리뷰어, FE 담당자
- **관련 기준:** 기능별 최신 승인 명세·Figma·기존 OPUS UI·실제 API 계약.
  - 코드가 제품 정책과 충돌하면 차이를 명시하고 임의로 테스트 기대값을 바꾸지 않습니다.

## 1. 목적과 원칙

**OPUS Browser QA는 실제 브라우저에서 핵심 사용자 행동과 그 결과를 재현·검증하여 프론트엔드 변경으로 인한 회귀를 예방하는 품질 관리 활동**입니다. 테스트는 개발자가 변경의 영향을 확인하고, 리뷰어가 검증 근거와 미검증 범위를 판단하도록 돕습니다.

1. **사용자 관점:** 클릭·입력·탐색·제출·피드백 등 실제 행동과 관찰 가능한 결과를 검증합니다. 단순 렌더링이나 스크린샷 생성만으로 완료 처리하지 않습니다.
2. **위험 기반:** 모든 화면을 똑같이 검사하지 않고 권한, 데이터 무결성, 핵심 흐름, 재작업 위험, 공통 UI 영향도를 기준으로 우선순위를 정합니다.
3. **재현성·격리:** 합성 데이터, 명확한 사전 상태, 독립적인 테스트로 동일한 동작을 반복 검증합니다.
4. **테스트와 제품 정책의 일치:** 기능 명세·API 계약이 바뀌면 관련 테스트와 Fixture도 함께 갱신합니다. 테스트에 맞추기 위해 제품 동작을 임의로 바꾸지 않습니다.
5. **검증 결과의 구분:** MSW 기반 Browser Test, 수동 Visual QA, 실제 백엔드 통합 검증은 서로를 대체하지 않습니다.

Playwright는 **사용자 행동과 화면 결과를 검증**하는 도구이고, MSW는 **테스트 조건에 맞는 API 응답을 제공**하는 도구입니다.

## 2. 범위와 용어

### 2.1 검증 범위

| 검증 활동                  | 주요 목적                                                                   | 이 활동만으로 보장하지 않는 것                       |
| -------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------- |
| **MSW 기반 Browser Test**  | 실제 프론트엔드에서 사용자의 행동·상태 변화·오류 표현·접근 제한 확인        | 실제 서버·DB·OAuth 동작, API 계약의 실재성           |
| **수동 Visual QA**         | 타이포그래피, 여백, 정보 위계, 반응형, 상호작용 상태 등 실제 화면 품질 검토 | 모든 브라우저·기기에서의 완전한 동작, 자동 회귀 차단 |
| **Visual Regression Test** | 승인된 기준 이미지와 현재 화면의 차이 감지                                  | 차이가 의도된 것인지, UX가 좋은지의 판단             |
| **실백엔드 E2E Test**      | 테스트 환경의 실제 API·인증·저장소를 연결해 업무 흐름 검증                  | 운영 환경 전체의 안전성·성능·접근성의 자동 보증      |

현재 로컬 구현은 **Chromium + 로컬 Vite + MSW + 도메인별 Playwright Test** 구성입니다. 실제 기기, Firefox·WebKit, 운영 서버, 전체 화면 스냅샷 비교는 자동으로 검증된다고 가정하지 않습니다. 로컬 테스트 통과와 원격 CI 통과는 별도로 기록합니다.

### 2.2 용어

| 용어                  | 정의                                                                                                                    |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Browser QA**        | 브라우저 기반 품질 확인 활동 전체. 자동화와 필요한 수동 검토 포함                                                       |
| **Browser Test**      | Playwright로 사용자 행동과 결과를 Assertion으로 확인하는 자동 테스트                                                    |
| **E2E**               | 연결된 시스템의 시작부터 끝까지를 검증하는 범주. 본 문서에서는 MSW 기반 Browser Test와 **실백엔드 E2E**를 구분하여 표기 |
| **MSW Handler**       | 지정된 HTTP 요청에 테스트 응답을 반환하는 Mock 처리기                                                                   |
| **Fixture**           | 테스트 데이터, 권한, 응답 상태, 공통 환경을 준비·격리하는 구성                                                          |
| **Scenario**          | 사전 조건(Given)·행동(When)·기대 결과(Then)의 묶음                                                                      |
| **Assertion**         | 사용자에게 보이는 결과·상태가 기대와 일치하는지 판단하는 검증식                                                         |
| **Smoke Test**        | 핵심 경로의 최소 동작을 빠르게 확인하는 검사. 모든 변경 UI의 검증이 아님                                                |
| **Visual QA**         | 실제 화면의 시각적·사용성 품질을 검토하는 작업                                                                          |
| **Visual Regression** | 기존 Baseline 이미지와 현재 이미지를 비교해 변화 탐지                                                                   |
| **Flaky Test**        | 동일한 코드·조건인데도 결과가 간헐적으로 달라지는 불안정한 테스트                                                       |
| **Baseline**          | 리뷰를 거쳐 채택한 시각적 비교 기준 이미지                                                                              |

## 3. 테스트를 언제 작성하는가

변경된 모든 파일에 테스트를 추가하지는 않습니다. **사용자 가치와 실패 영향도**를 먼저 고려하고, 해당 기능의 기존 테스트가 있다면 같은 PR에서 유지·보완합니다.

| 변경 유형                                        | 기본 기준                                                         | PR에 필요한 근거                           |
| ------------------------------------------------ | ----------------------------------------------------------------- | ------------------------------------------ |
| 문구·색상·간격처럼 순수 표현 변경                | **수동 Visual QA**. 기존 Browser Test가 영향받으면 재실행         | 변경 화면 이미지, 확인한 크기·상태         |
| 단일 버튼·모달·드롭다운 인터랙션                 | 수동 행동 검증. 오류 가능성·반복성이 높으면 **Browser Test 권장** | 조작 결과·키보드/모바일 등 해당 범위       |
| 생성·수정·삭제·제출·다운로드 등 핵심 데이터 흐름 | **관련 Browser Test 작성/수정 우선 고려**                         | 정상·주요 실패 결과, 저장/갱신 상태        |
| 권한별 접근·버튼 제한·개인정보 노출              | **관련 Browser Test 작성/수정 우선 고려**                         | 허용·거부 역할과 결과, 보안 검토 필요 여부 |
| 평가 설정 등 다단계 상태 전환                    | **핵심 성공 경로와 중요한 실패/복구 경로 자동화 우선 고려**       | 단계별 사용자 관찰 결과                    |
| 공통 컴포넌트·라우터·인증·전역 스타일 변경       | 영향받는 기존 테스트 재실행 + 대표 UI 수동 점검                   | 영향 범위와 미검증 화면                    |
| 내부 구조만 바뀌고 사용자 동작이 동일            | 기존 관련 테스트 실행. 신규 테스트는 위험에 따라 결정             | 동일 동작을 확인한 근거                    |

자동화 여부는 변경 위험과 재현 가능성을 기준으로 판단하며, 모든 변경에 신규 테스트를 강제하지 않습니다. 수동 검증을 선택하면 확인한 범위와 판단 근거를 PR에 남깁니다. 재현 환경이 없거나 실제 백엔드에 의존하여 검증하지 못한 항목은 사유와 후속 범위를 명시합니다. 이미 테스트가 있는 주요 사용자 흐름을 변경하면서 아무 검증 없이 테스트를 삭제해서는 안 됩니다.

### 3.1 개발자와 리뷰어의 책임

- **변경 담당 개발자:** 관련 명세·API 계약을 확인하고 검증 시나리오를 선정합니다. 필요한 테스트를 추가·수정하고 자동·수동 검증 결과 및 미검증 항목을 PR에 남깁니다.
- **PR 리뷰어:** 테스트가 변경 위험에 맞는지, 사용자 관점 Assertion이 있는지, Mock이 실제 정책을 왜곡하지 않는지 확인합니다. UI 변경은 실제 화면 근거도 검토합니다.
- **FE 담당자:** 여러 도메인에서 재사용하는 Fixture, CI 정책, 반복되는 Flaky Test 및 테스트 기술 부채를 관리합니다.
- **백엔드 담당자와 협의:** 응답 형식, 권한, 데이터 저장·삭제, 실패 코드 등 계약이 불분명할 때 합의합니다. Mock을 사실상의 API 명세로 사용하지 않습니다.

### 3.2 PR의 QA 완료 기준(Definition of Done)

**자동 Browser Test를 추가·수정한 PR**은 다음을 만족해야 합니다.

- [ ] 핵심 시나리오에 명확한 사전 상태·행동·기대 결과가 있고 테스트가 독립적으로 실행됩니다.
- [ ] 정상 결과뿐 아니라 변경으로 영향받는 중요한 오류·권한·빈 데이터 상태를 확인했습니다.
- [ ] 테스트·Fixture에 실사용자 정보, 운영 토큰, 운영 URL을 포함하지 않았습니다.
- [ ] 관련 도메인 테스트와 타입/빌드 등 필수 검증을 실행하고 결과를 기록했습니다.
- [ ] 예상하지 못한 실패·Flaky Test를 방치하지 않았고, 불가피한 미검증 항목은 사유와 후속 작업을 명시했습니다.
- [ ] UI를 변경했다면 실제 변경 화면을 브라우저에서 확인하고 필요한 캡처·영상·뷰포트를 첨부했습니다.

**수동 QA만 수행한 PR**은 테스트를 작성하지 않은 이유와 실제 확인한 화면·행동·상태를 남깁니다. CI 통과만으로 변경 화면을 검증 완료라고 표시하지 않습니다.

## 4. 새 Browser Test 작성 원칙

### 4.1 준비와 설계

1. 최신 승인 기능 명세, 실제 화면·접근 권한, 사용 API DTO·핸들러를 확인합니다.
2. 테스트할 **사용자 행동**과 **그 후에 보이는 결과**를 Given–When–Then 형식으로 정의합니다.
3. 정상 경로, 중요한 실패 경로, 권한, 로딩·빈 데이터 중 **해당 변경에 실제로 영향을 받는 경우**를 선정합니다.
4. 기존 테스트·공통 Fixture가 있는지 검색하고 중복을 방지합니다.
5. 기능 도메인의 테스트 파일에 시나리오를 작성합니다. 공통 설정에 모든 테스트 이름·URL을 수동 등록하는 구조는 피합니다.

### 4.2 테스트 코드 기준

- 일반 도메인 테스트는 **반드시 `fixtures/test`에서 `test`, `expect`를 가져옵니다.** `tests/browser/<domain>/*.spec.ts` 기준 경로는 `../fixtures/test`입니다. 네트워크 가드·MSW 준비 확인·JavaScript 오류 검사·진단 수집은 이 공통 Fixture에 있으며, `@playwright/test`의 `test`를 직접 사용하면 적용되지 않습니다. 인프라 검증처럼 가드를 직접 설치하고 차단 결과를 검사하는 테스트는 목적이 명시된 예외입니다.
- 테스트명은 **행동 + 기대 결과**로 작성합니다. 예: `잘못된 비밀번호 입력 시 로그인 화면을 유지하고 오류를 표시한다`.
- `getByRole`, `getByLabel`, `getByPlaceholder` 등 사용자 관점 Locator를 우선합니다. 동일한 텍스트가 많으면 범위를 좁힙니다. 안정적인 접근성 이름이 없다면 UI 자체의 접근성을 먼저 검토합니다.
- `waitForTimeout()`으로 시간을 추측하지 말고 `expect(...).toBeVisible()`, `toHaveURL()`, `toBeEnabled()` 같은 자동 재시도 Assertion을 사용합니다.
- `expect` 없이 클릭만 하거나 스크린샷만 찍는 테스트는 기능 성공을 증명하지 못합니다.
- `page.route().fulfill()`로 테스트마다 제2의 API Mock 체계를 만들지 말고 기존 MSW와 시나리오 Fixture를 우선 사용합니다. 네트워크 차단·격리 검증 등 정당한 예외는 목적을 문서화합니다.
- 테스트 순서, 개발자의 브라우저 상태, 앞선 테스트가 만든 데이터에 의존하지 않습니다. 테스트별 초기 상태를 만들고 필요하면 정리합니다.
- 너무 많은 UI를 한 번에 검증하는 거대 테스트를 피합니다. 다만 실제 한 업무 흐름의 상태 전환은 하나의 의미 있는 테스트로 묶을 수 있습니다.
- 실패를 감추기 위한 임의의 `try/catch`, 무조건적인 `skip`·`only`, 과도한 retry·timeout 증가는 금지합니다.

### 4.3 OPUS 실제 사례로 보는 좋은·나쁜 예시

아래는 현재 로컬의 OPUS UI와 공통 Fixture를 사용하는 예제입니다. 실제 테스트 파일은 [대회 테스트](../tests/browser/contest/list.spec.ts)와 [인증 테스트](../tests/browser/auth/sign-in.spec.ts)에서 확인할 수 있습니다. 인증 테스트에는 온보딩 확인, 로그인 오류 후 재시도, 역할별 메뉴, 서버 오류 시나리오가 포함되어 있습니다.

**나쁜 예 — 촬영만 하고 성공으로 판단**

```ts
// 잘못된 예시: 사용자 행동과 기대 결과를 전혀 검사하지 않음
import { test } from '../fixtures/test';

test('로그인 QA', async ({ page }) => {
  await page.goto('/signin');
  await page.screenshot({ path: 'login.png' });
});
```

**좋은 예 — 실제 OPUS 내비게이션 결과를 검증**

```ts
// tests/browser/<domain>/*.spec.ts에서 사용하는 형태
import { test, expect } from '../fixtures/test';
import { expectMswReady } from '../support/ready';

test('홈에서 로그인 버튼을 누르면 로그인 화면으로 이동한다', async ({ page }) => {
  await page.goto('/');
  await expectMswReady(page);
  await page.getByRole('button', { name: '로그인 / 회원가입', exact: true }).click();
  await expect(page).toHaveURL('/signin');
});
```

위 예제의 이동 동작은 현재 대회 테스트에서도 검증합니다. 다른 도메인으로 확장할 때는 실제 UI의 접근성 이름과 해당 화면의 초기 상태를 확인하세요.

**OPUS 로그인 오류 시나리오의 설계 기준:** 실제 `src/mocks/handlers/sign-in.ts`는 알려진 합성 이메일과 비밀번호 `test` 조합에 성공 응답을 주고, 그렇지 않으면 HTTP 400을 반환합니다. 인증 테스트는 응답 코드와 함께 **오류 안내와 로그인 화면 유지**, 올바른 비밀번호로 재시도한 뒤 홈 이동을 검증합니다. 별도의 `auth/unavailable` Fixture는 로그인 API에 HTTP 503을 반환합니다. Fixture 선택 방법은 [구현 문서의 시나리오 작성 안내](./browser-qa-implementation.md#32-시나리오-fixture-작성과-선택)를 따릅니다.

## 5. MSW·Fixture 운영 정책

### 5.1 단일 Mock 체계 유지

기본 원칙은 **기존 `src/mocks/handlers/`와 `src/mocks/data/`의 재사용**입니다. `tests/browser/fixtures/`에서 필요한 상태만 덮어쓰되, 엔드포인트·HTTP 메서드·응답 DTO·상태 코드가 실제 계약과 어긋나지 않아야 합니다.

- **기본 성공 상태:** 기존 MSW 데이터·핸들러를 먼저 활용합니다.
- **빈 데이터/오류/권한 상태:** 시나리오의 목적이 명확한 경우에만 Fixture로 구분합니다.
- **쓰기·상태 전이:** 테스트가 `생성 → 목록 반영`을 검증한다면 고정 응답으로 성공만 반환하지 말고, 해당 테스트가 관찰할 수 있는 상태 변경을 재현합니다. 초기 상태와 테스트 간 격리를 함께 설계합니다.
- **동시 실행:** 서로 다른 테스트의 쓰기 상태를 전역 변수·공유 파일에 저장하지 않습니다. 순서 또는 테스트 파일별 실행 방식에 의존하지 않습니다.
- **핸들러 우선순위·재설정:** 테스트 종료 후 오버라이드가 남지 않음을 검증합니다. 여러 시나리오를 조합한다면 우선순위를 명시하고 충돌을 피합니다.
- **새로고침과 쓰기 상태:** 현재 구조는 문서가 새로 만들어질 때 선택한 시나리오를 다시 적용합니다. Fixture 모듈의 메모리상 쓰기 상태는 초기화되므로, 새로고침 후 저장 결과까지 검증하려면 테스트 내 지속 상태를 별도로 설계해야 합니다. 시나리오 재적용을 데이터 영속성으로 해석하지 않습니다.
- **미처리 요청:** 의도하지 않은 API 요청을 무조건 성공 응답으로 우회하지 않습니다. 차단 여부와 오류 진단은 네트워크 정책을 따릅니다.

### 5.2 API 계약과 제품 정책

Mock 응답의 타입이 맞더라도 실제 API 계약을 충족한다고 단정하지 않습니다. 신규·변경 API에서는 성공/오류 코드, 필수 필드, 권한, 저장 후 조회 결과를 백엔드와 대조합니다. 계약이 미확정이면 테스트 기대 결과를 확정한 것처럼 쓰지 않고 PR에 미결정 사항을 남깁니다.

예를 들어 기존 `src/mocks/handlers/contest.ts`의 **팀 일괄 등록 API**는 오류 응답(400)을 고정으로 반환합니다. 이를 모든 상황의 표준 정책으로 간주하지 말고, 실제 성공·오류 계약을 확인한 뒤 시나리오별 상태를 구성해야 합니다.

### 5.3 보안과 데이터 취급

운영 URL, 실제 계정·개인정보·토큰, 실데이터 덤프를 사용하지 않습니다. 네트워크는 기본적으로 로컬 앱 리소스와 승인된 필요 리소스만 허용하고, 실제 API·외부 서비스 요청은 차단해야 합니다. Trace는 DOM·네트워크·콘솔을 담을 수 있으므로 **진단 메시지에 민감정보가 없더라도 Trace 자체는 공유 전 검토**합니다.

## 6. CI 실행 및 실패 대응

### 6.1 기본 실행 원칙

- **로컬:** 변경 도메인 테스트를 먼저 수행하고, 관련 공통 테스트를 추가로 확인합니다.
- **PR:** 구현된 CI가 대상으로 하는 Browser Test를 실행합니다. 테스트가 아직 없는 기능은 CI에서 자동 검증되었다고 주장하지 않습니다.
- **공통 코드 변경:** 인증·라우터·공통 컴포넌트·Mock 기반을 수정하면 관련 도메인의 회귀 위험을 검토합니다.
- **실패 증거:** 실행 로그, Assertion, 스크린샷, Trace를 우선 확인합니다. 정확한 스크립트·아티팩트 경로는 [구현 참고 문서](./browser-qa-implementation.md)에 둡니다.

워크플로우 파일을 수정하거나 로컬에서 CI 설정으로 테스트를 실행한 것만으로 원격 CI가 통과했다고 기록하지 않습니다. GitHub Actions 실행 결과는 해당 PR의 실행 링크와 함께 기록합니다.

### 6.2 실패 분류 및 조치

| 실패 유형       | 판단 기준                                        | 기본 조치                                                       |
| --------------- | ------------------------------------------------ | --------------------------------------------------------------- |
| **제품 결함**   | 실제 기대 동작·권한·화면 상태와 불일치           | 제품 코드를 수정하고 재실행                                     |
| **테스트 결함** | 낡은 Locator, 잘못된 기대값, Fixture 오류        | 최신 명세·UI·DTO 확인 후 테스트 수정                            |
| **환경 문제**   | 브라우저 설치, 포트 충돌, MSW 준비, 외부 폰트 등 | 환경 재현·격리 원인 수정. 제품 문제로 오판하지 않기             |
| **Flaky Test**  | 동일 변경 없이 실행마다 성공·실패 교차           | 반복 실행·Trace로 경쟁 상태와 공유 상태 조사. 원인 및 이슈 기록 |
| **미확정 계약** | 테스트 기대와 백엔드 명세가 충돌/부재            | 담당자 협의, 미확정 내용 기록, 자의적 기대값 수정 금지          |

실패 시 **(1) 재현 → (2) 실패 유형 분류 → (3) 원인 수정 → (4) 관련·영향받는 테스트 재실행 → (5) PR에 근거 기록** 순서로 처리합니다. 재실행 성공만으로 Flaky Test를 완료 처리하지 않습니다. `skip`은 사유·이슈·복구 조건을 기록한 예외 상황에서만 사용하고, `only`는 커밋하지 않습니다. 재시도 설정은 실패 은폐가 아닌 간헐적 실패 탐지를 위한 수단으로 사용합니다.

### 6.3 PR에 남길 최소 증거

- 변경 기능 및 영향받는 사용자 흐름
- 자동 검증: 실행한 명령·테스트 범위·결과(또는 실행 불가 이유)
- 수동 UI 검토: 화면·뷰포트·중요 상태, 필요 시 Before/After 이미지
- Mock/실백엔드 범위와 계약 미확정 사항
- 실패·Flaky Test·미검증 항목과 후속 이슈

## 7. 도메인별 테스트 관리

- **위치:** `tests/browser/<domain>/<feature>.spec.ts` 같은 도메인별 구성을 권장합니다. 실제 파일 경로와 Runner 적용 상태는 [구현 문서](./browser-qa-implementation.md)를 확인합니다.
- **소유권:** 기능을 수정한 개발자가 관련 테스트를 수정하고, 리뷰어가 기대 결과·Mock의 적합성을 확인합니다.
- **변경 동기화:** 제품 정책, 권한, UI 이름, API DTO가 변경되면 해당 테스트를 같은 PR에서 검토합니다.
- **중복 제거:** 명확히 공통인 환경만 Helper/Fixture로 추출합니다. 거대한 범용 Page Object나 비즈니스 로직 중복 구현을 피합니다.
- **삭제 기준:** 기능 제거·정책 폐기·동등 검증으로 대체된 경우에만 삭제하고 이유를 PR에 남깁니다.
- **테스트 자산의 상태:** 정상 동작하던 테스트가 제품 변경으로 실패했다면 ‘불편한 테스트’가 아니라 변경 영향 분석 대상으로 취급합니다.

## 8. Visual Regression 정책 — 도입 기준과 확장

**현 단계의 기본 요구는 수동 Visual QA입니다.** 자동 이미지 비교는 다음 조건을 충족하는 안정화된 화면부터 **후속 도입**합니다.

1. **대상 선정:** 공통 컴포넌트, 핵심 화면, 반복적인 시각적 회귀가 발생하는 화면을 우선합니다. 모든 페이지·상태의 스냅샷을 목표로 하지 않습니다.
2. **재현 조건:** 뷰포트·OS·브라우저 버전·폰트·로캘·시간·데이터를 고정합니다. 애니메이션·비동기 콘텐츠를 안정화합니다.
3. **Baseline 승인:** 최초 이미지는 담당 개발자와 리뷰어가 실제 디자인 정책·화면을 확인한 뒤 승인합니다.
4. **차이 검토:** 이미지 Diff가 발생하면 의도된 디자인 변경인지 회귀인지 판단합니다. `--update-snapshots`로 무조건 덮어쓰지 않습니다.
5. **기준 변경:** 승인된 변경에 한해서만 Baseline을 갱신하고 PR에 차이·승인 근거를 남깁니다. Diff를 통과시키기 위해 임계값을 과도하게 완화하지 않습니다.
6. **실패 대응:** 렌더링 환경 차이, 동적 콘텐츠, 폰트 로딩 등 테스트 불안정 요인과 실제 UI 결함을 구분합니다.

향후 Playwright의 `expect(page).toHaveScreenshot()`을 사용할 수 있지만, **현재 이 기능이 OPUS CI에 적용되었다는 뜻은 아닙니다.** 스냅샷만으로 접근성·사용성·기능 동작 검증을 대체하지 않습니다.

## 9. 실백엔드 E2E 정책 — 도입 기준과 확장

MSW 기반 Browser Test는 UI 동작을 반복 재현하는 데 유리하지만, 실제 HTTP 계약·인증·DB 상태는 확인하지 못합니다. 따라서 **실백엔드 E2E는 별도의 격리된 검증 단계**로 설계합니다.

**도입 선행 조건**

- 운영과 완전히 분리된 테스트 서버·DB 및 데이터 초기화/정리 방법
- 테스트 전용 합성 계정과 역할(학생·교수·관리자 등 해당 흐름에 필요한 범위), 안전한 인증 처리
- 테스트 대상 API 계약의 합의, 저장·삭제가 다른 테스트에 영향 주지 않는 격리 전략
- CI Secret 관리 및 접근 권한 제한, 운영 데이터·실사용자 계정 사용 금지
- 실패 시 테스트 데이터·파일 업로드 잔여물 정리, 테스트 환경 복구 절차

**우선 검증할 흐름**은 인증·권한, 제출물 저장/수정, 평가 설정·점수 저장, 투표처럼 실제 서버 계약과 상태 무결성이 중요한 경로입니다. 단, 기능별 승인 명세와 백엔드 구현 준비 상태를 확인한 후 적용합니다.

**운영 방법:** 로컬 MSW 테스트와 실백엔드 E2E를 별도 프로젝트/워크플로우로 구분합니다. 초기에는 수동 실행 또는 격리된 검증 환경에서 소규모로 시작하고, 안정성과 실행 비용을 확인한 뒤 필수 CI 여부를 결정합니다. CI 통과 범위에는 실제 연결된 구성요소와 제외된 외부 서비스(OAuth 등)를 명확히 적습니다.
